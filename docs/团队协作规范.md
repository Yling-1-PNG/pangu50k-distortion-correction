# 盘古 50K 赛题二团队协作规范

本文件是仓库内的人与 Codex 的共同工作约定；以 `docs/紫光赛题.pdf` 确认赛题，以本仓库的实际代码、构建日志和实物测试记录确认完成状态。聊天记录可以辅助解释决策，不取代仓库中的源文件与证据。

## 1. 唯一项目与分工

- 每位成员在自己的电脑克隆同一私有仓库，用 VS Code 和各自登录的 Codex 工作。不要共享 ChatGPT/GitHub 账号，也不要用网盘同步一个正在编辑的 Git 工作目录。个人电脑上的绝对路径可以不同；提交的脚本优先使用相对路径。
- 目前集成主机持有盘古 50K 和 PDS Lite，负责板上接线、下载、DDR3/HDMI/摄像头实测与最终位流。无板卡成员可以并行负责真实棋盘格取样分析、PC 黄金模型、RTL 单元/仿真、上位机和测试文档。任务分配随实际成员数量调整，不预设某人完成未经确认的模块。
- 同一时段不要让两个人直接改同一条主线的接口定义或生成同一份方案 PDF。改动相机参数 JSON、像素格式、坐标方向、帧缓存时序等共享接口前，先在任务/PR 中给出输入输出契约，并通知集成负责人。

## 2. 分支与合并

1. `main` 保持可复现的基线；每个明确任务从最新 `main` 建短分支，例如 `feat/fisheye-calibration`、`rtl/coordinate-map`、`test/linearity`。
2. 每个分支只解决一件事。提交前运行相关测试、检查变更文件及 `git diff --check`；不要把另一个人的本地改动、资料包或构建目录混入提交。
3. 通过 Pull Request 写明“目标、改了什么、测试命令与结果、板卡验证状态、未解决问题”。至少由另一名成员检查接口与证据后合并；若团队暂只有一人，保留 PR/自检记录。
4. 合并后在集成主机复跑 PC 测试，涉及 RTL/PDS 再做离线构建；涉及外设或性能才按计划进行实板验证。Codex 可以协助读代码、写测试和审查差异，但提交与硬件结论由成员确认。
5. 一项需要并行的 Codex 任务可使用 Git worktree；它只隔离本机工作目录，跨成员同步仍依赖 Git 远端和 PR。切勿把两个 worktree 的生成目录当作同一份输出。

## 3. 文件边界与复现

- 应跟踪：`AGENTS.md`、`README.md`、`docs/*.md`、赛题及方案 PDF、`tools/*.py`、底稿 `tools/assets/initial_plan_base_17p.pdf`，以及未来正式的 RTL、仿真、PDS 项目配置、引脚/时序约束和 IP 配置。普通模型与鱼眼模型参数格式须显式标识，不能混用。
- 不跟踪：`build/` 中的位流、日志、解压的参考工程和 PDS 生成物，完整厂家资料包，原始相机照片/视频，账号令牌、授权文件和本机 IDE 配置。少量可公开的测试图片若要入库，先确认来源、体积和授权；大样本采用经团队同意的共享存储或 Git LFS，并留索引与版本。
- 厂家例程需在新成员机器上从官方资料包恢复；当前仓库尚**没有正式 FPGA 矫正源工程**。不要把 `build/` 中已离线构建的官方视频搬运例程报告成赛题 RTL 已完成。
- PDF 方案以同名 Markdown 为正文来源，由一名集成负责人统一生成和核验。`tools/append_plan_update.py` 及其底稿用于保留原 17 页历史页面；更新 PDF 后检查新页排版、页数和既有页内容。不要直接编辑已生成 PDF 造成 MD/PDF 不一致。

## 4. 测试与证据等级

PR 和进度记录采用下列状态，不能跨级推断：

| 状态 | 可以声称 | 不能声称 |
| --- | --- | --- |
| PC 单元测试 | 浮点模型/脚本在所列环境和输入下通过 | 相机真实标定或 FPGA 已运行 |
| PDS 离线构建 | 指定工程与约束生成网表、实现或位流 | 板上出图、全 IO 时序已闭合 |
| 板上功能测试 | 指定板卡修订、接线、分辨率和时长下观察到结果 | 未测的帧率、延迟、MTF50/SFR |
| 量化验收 | 附原始帧、标定、时序、帧率/延迟和画质方法的数据 | 其他镜头、模式或分辨率自动达标 |

鱼眼到货后先保存**相机原始帧**，再标定与比较有效视场；手机拍显示器的照片只作选型线索。赛题指定的二阶径向/切向基础模型和鱼眼扩展模型都要有独立验证。硬件操作应先核对 IO 电平和引脚，不能仅因参考位流生成成功就直接烧录。

## 5. Codex 协作提示

每个成员在新聊天中指向自己的仓库根目录，描述清楚：目标、允许修改的文件、验收命令和是否允许板卡操作。例如：“只修改 `tools/fisheye_model.py` 与对应测试，保持 Brown 分支不变；运行两套测试；不声称实板验证。”让 Codex 先阅读本仓库 `AGENTS.md` 与本任务相关文档；复杂工作用 `task_plan.md`、`progress.md` 记录状态，但避免为小改动反复更新长文档。

遇到冲突或疑似多份工程时，以仓库和最近合并的主线为准，不覆盖队友未提交的更改。仓库远端地址、成员权限和相机真实参数，以当时实际配置和实测为准。
